# 教程：手写一个代码库 RAG（能跑的版本）

这个目录是一个**可以逐行读、逐条改、立刻看到结果**的最小实现。
零依赖（只用 Python 标准库），不装包、不下模型、不联网。

它刻意做得不完整 —— 每一处「这里是假的」都写清了为什么假、
真的应该是什么。读完你应该能自己判断哪些设计该保留、哪些该换掉。

## 跑起来

```bash
cd tutorial
python3 1_chunk.py                        # 切片
python3 2_index.py                        # 建索引
python3 3_retrieve.py "verify_password"   # 检索，看三路排名和融合过程
python3 4_ablation.py                     # 消融实验（最有价值的一步）
python3 5_ask.py "登录时密码是怎么校验的" # 看模型实际收到的 prompt
python3 6_update.py                       # 增量更新，看幽灵 chunk 怎么产生
```

`3_retrieve.py` 可以换问题反复试，加 `--only vector` 之类的参数看单路表现。

## 六步，每步看什么

| 脚本 | 核心问题 | 跑完重点看 |
|---|---|---|
| `1_chunk.py` | 怎么把代码切成块 | 被排除了哪些文件、chunk 的面包屑长什么样、calls 抽到了什么 |
| `2_index.py` | 怎么让 chunk 能被查到 | 英文 vs 中文在 FTS5 里的表现对比；「被谁调用」为什么必须查表 |
| `3_retrieve.py` | 三路结果怎么合并 | 同一条 chunk 在三路里的排名差异；RRF 得分的手算过程 |
| `4_ablation.py` | 每一路到底贡献多少 | 那张命中率表，以及「为什么向量是兜底不是主力」 |
| `5_ask.py` | 模型到底收到了什么 | 完整 prompt；检索为空时的兜底处理 |
| `6_update.py` | 代码变了怎么跟上 | 幽灵 chunk 是怎么产生的，删除要清几张表 |

**如果只读一个，读 `4_ablation.py` 的输出。** 它会用数字告诉你
「精确命中 > BM25 > 向量」这句话是怎么来的，而不是让你相信我。

## 玩具库里埋了什么

`toy_repo/` 是个极简电商后端，故意塞进了真实项目里最烦的四种情况：

- **同名符号**：`api/login.py` 和 `service/user_service.py` 各有一个
  `validate_user`，做的事完全不同 → 对应「目录过滤」
- **跨文件调用**：`verify_password` 被 `UserService.login` 调用
  → 对应「calls 表」
- **生成代码**：`generated/api_client.py` 内容不少但不该进索引
  → 对应「三层排除规则」
- **中文查询**：用中文问「密码怎么校验」，和 `verify_password`
  在字符层面毫无重叠 → 对应「假向量的边界」

## 从玩具到真实：要换什么

| 教程里的做法 | 真实工程应该用什么 | 为什么必须换 |
|---|---|---|
| Python 内置 `ast` | tree-sitter | 只支持 Python；真项目要吃 TS/Go/Java |
| 字符 3-gram 假向量 | BGE-M3 / Qwen3-Embedding-4B | 假向量只认字符重叠，中英之间完全不通 |
| 纯 Python 算余弦（O(n) 全表扫） | sqlite-vec，量大了换 Qdrant | 33 条无所谓，30 万条每次查询扫全表会卡死 |
| 每次重建整库 | 文件 sha256 比对 + git hook | 见 `6_update.py`，不过这关工具三个月就废 |
| 无重排 | bge-reranker-v2-m3（top-20 → top-5） | 命中率卡在 70~80% 时的第一手段 |
| 单文件脚本 | `../src/code_rag/` 那套骨架 | 骨架是同一个流程的工程化版本 |

换的优先级：**先换 embedding 模型，再换存储**。
前者决定效果上限，后者只在量大了才成为瓶颈。

## 三个坑（本教程亲手演示给你看的）

**1. 中文在 FTS5 里天然失效。**
默认分词器按空格切词，中文没有空格，整句会被当成一个 token，
于是搜「密码」永远搜不到「校验用户密码」。
`2_index.py` 里的 `expand_cjk` 用 2-gram 展开解决了它 —— 零依赖版，真实工程可以换 jieba。

**2. BM25 用 OR 连接查询词，于是永远有结果。**
问一个库里根本没有的东西，照样能返回一堆片段，
模型拿到上下文就开始一本正经地编。所以 OR 策略必须配套相关性门槛，
或者干脆上重排模型 —— 靠 bm25 的绝对分数切是不可靠的，
它的值不能跨查询比较（问句越长，累积分越高）。

**3. 召回深度必须大于最终返回的条数 —— 亲手看一次排序反转：**

```bash
python3 3_retrieve.py "verify_password" --depth 1
```

每路只召 1 条时，融合结果是：

```
test_verify_password_survives_malformed_hash   BM25第1 + 向量第1  ->  0.03279
verify_password                                精确第1            ->  0.01639
```

**问符号名，符号自己输给了一个测试函数。** 原因有两层：

- RRF 只看排名，BM25 和向量的两票压过了精确路的一票
- 深度只有 1，`verify_password` 在另两路里排第 2、第 5 的事实被抹掉了

去掉 `--depth`（回到默认 15 条）再跑，第一名就变回 `verify_password` ——
它在三路里分别是第 1、第 2、第 5，合计 0.04791。脚本会直接打出这个对照。

真实工程每路常召回 top-50 ~ top-200，最后只给用户看 5 条，就是为了
保住「在多路里都排得靠前」这个信号。

顺带一条真实工程必须处理的推论：**全名精确命中要走短路、直接置顶，
不能老老实实去参与融合。** 用户问符号名时就是要那个符号本身，
这时「提到这个词的地方」拿到再多票也不该赢。

## 和 `../src/` 骨架的关系

`../src/code_rag/` 是同一套流程的工程化版本，分了模块、定义了接口，
但目前只有 TODO 骨架没有实现。

建议的顺序：**先在这个教程里把每一步跑通、改坏、再修好**，
然后回头看骨架，你会发现那些 TODO 为什么是那样列的。
